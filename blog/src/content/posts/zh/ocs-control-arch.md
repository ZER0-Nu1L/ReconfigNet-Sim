光电路交换机（Optical Circuit Switch，OCS）正在跨过毫秒级重构的门槛。2025 年 3 月，OFC 展会前夕，iPronics [发布 ONE-32](https://ipronics.com/ipronics-unveils-worlds-first-silicon-photonics-optical-circuit-switch-for-ai-driven-data-centers-optical-network-transformation/)，将它称为“全球首款基于硅光的 OCS”，并给出**小于 300 μs 的快速重构承诺**，微秒级切换由此成为面向数据中心的产品卖点。

**更快的切换，意味着光交换可以赋能更多应用。** 在 OCP 的[快速 OCS 演讲](https://drive.google.com/file/d/1G0o39qR0wZvvHHfMTyiAe2mB6j5HxelF/view)中，Lumotive 的 James Burch 与 iPronics 的 Vivek Sarathy 用“Faster Switching Expands its Use Cases”概括这一变化：当重构进入亚毫秒级，光连接就有机会随流量需求和 AI 通信阶段更频繁地调整，服务于动态流量疏导、阶段间拓扑适配和更细粒度的光路调度。速度的意义，在于让原先受重构等待限制的用法变得值得探索。

与此同时，**沿用已有电交换网络的 SDN 编排方式和控制架构，是当前产业集成方案中一个清晰可见的方向。** iPronics 的 Iwan Kartawira（[OCP OCS 子项目负责人之一](https://www.opencompute.org/community/optical-circuit-switching)）与 KDDI 的 Kazuaki Ueda 在[多厂商 OCS 用例演讲](https://drive.google.com/file/d/1ahYwnygxq6vzFGNZWNrXO7r9fLLhCvg7/view)中明确提出“CPO + OCS + SDN”，将工作负载优化放在 SDN 与 OCS 协同的架构中；其多厂商控制路径由 gNMI 客户端进入设备的 gNMI 服务与通用 YANG 数据存储，再对接厂商 API。统一模型、控制器与既有管理协议，构成了这条集成路线的骨架。

但当 OCS 要随通信阶段频繁重构时，**完整沿用面向电交换网络的 SDN 配置流程，可能让控制路径成为重构速度的主要限制。** 在逐次经控制器协调的实现里，应用先请求控制器，控制器协调资源，再调用设备代理（OCS Agent）；设备实现还可能通过本地服务和 SDK 执行操作。全局管理和厂商适配各有价值，但每一跳也会引入额外的通信、校验、调度和排队。

以传统 3D MEMS 的毫秒级向硅光的亚毫秒级演进为背景，考虑这样一笔账：**假设 OCS 物理重构从 20 ms 降到 200 μs，串行控制路径仍需 5 ms，完整重构的等待就从 25 ms 降到 5.2 ms。器件快了 100 倍，整体只快约 4.8 倍。** 当控制架构仍按较慢的配置周期组织，每次执行却需要跟上通信调度时，沿用的控制路径就会吞掉器件迭代带来的大部分提速空间：**器件已进入微秒级，完整重构仍停留在毫秒级。**

![器件提速 100 倍，完整重构只提速约 4.8 倍](/ReconfigNet-Sim/images/ocs-control-arch/time-budget.svg)

*图 1：左右两侧分别比较器件重构与完整重构，条形图使用相同的毫秒刻度。物理过程从 20 ms 降到 0.2 ms，串行控制成本始终为 5 ms，其占总等待的比例从 20% 升至约 96%。这是显式假设下的算例，未计端侧恢复。*

上面算例中的落差，**根源在于控制架构与快速重构使用方式的不匹配。** 在典型的 SDN 电分组网络中，集中式控制器负责全局资源协调和规则配置，交换机硬件负责持续转发。这种架构兼顾了集中管理与高速转发：一次配置可以服务大量后续通信，控制成本得以摊薄，因此通常对单次配置开销相对不敏感。

而对于随通信阶段频繁重构 OCS 的应用，连接配置直接决定下一阶段何时能够发送数据。如果仍让每次重构经过完整的远程协调和设备配置流程，原本可以摊薄的控制成本，就会成为每轮通信必须支付的等待。**直接沿用这种配置流程，会使控制架构与 OCS 快速切换场景产生严重的时间尺度错配。** 回到算例：物理重构已经压缩到 200 μs，5 ms 的控制路径却原封不动，成本结构完全倒置——等待的大头不再是器件动作，而是控制软件本身。

OCP 社区正在推动统一模型、多厂商互操作和端到端指标，而本文要追问的是：**当配置成为每轮通信的必经步骤，现有的控制架构本身是否还合适？**

> [!TLDR]
>
> - **算完整路径的时间账。** 器件切换之外，请求处理、软件交接和设备调用同样决定何时能用上连接。物理重构从 20 ms 降到 200 μs 时，5 ms 的串行控制会让完整重构仍停在毫秒级。
> - **分别选择三个维度。** 控制器怎样参与、采用什么接口与协议、设备怎样执行，彼此可以独立换边，但都应由场景和时间预算决定。
> - **用 Tofino 实验核对成本。** 实测显示，精简上层后完整 API 延迟可从约 6.59 ms 降到 4.39 ms，而厂商运行时调用仍占剩余时间的大头；绕过控制器的收益与光器件并行收敛尚未测量。
> - **认清软件路径的下限。** 把协议与进程优化压到极限，通用 CPU 与管理协议形态的软件路径约为 20 μs（p99），再快就需要驱动级或 FPGA 方案。

## 一次重构：从规划决策到设备执行
把 OCS 集成到网络中，首先要决定连接哪些端口、什么时候改变连接，以及怎样与应用的通信阶段配合；随后，系统需要把这个决定交给设备，并完成实际重构。前者属于拓扑规划与调度，后者属于触发与执行。**规划可以提前完成，执行在需要时触发。** 目标可预测时，可以先算好连接；随需求到达才确定目标时，则需要在线决策。本文关心的是：目标已经确定以后，系统还要走多长的执行路径，才能让应用用上它？

执行通常从一条连接请求开始：请求经过必要的协调，到达设备控制服务；设备软件检查目标与权限，调用 SDK 或底层控制接口，把端口连接转成可执行的器件状态。不同 OCS 在这里有不同实现。

> - Google 的 [Mission Apollo](https://arxiv.org/abs/2208.10041) 描述了一个具体的 MEMS 例子：CPU 接收端口连接命令，经 FPGA 和高压驱动板设置微镜电压，再利用相机反馈调整镜面，使光路达到合适状态。
> - 对于可编程硅光网格，目标还需要映射成内部路径和可编程单元的状态；[λλ](https://dl.acm.org/doi/10.1145/3789240.3829151) 就将高层程序转为图表示，再求解它到目标光子硬件的映射。
> 两个例子都把连接意图落实为器件行为，只是中间需要完成的工作不同。

即使设备按接口约定报告了结果，也要区分四个时刻：**收到请求、编程完成、光路稳定、应用可用**。下图展示这些职责及其依赖。

## 时间预算：器件之外，还要等多久？
有了这个框架，开头那 5 ms 就可以继续拆开。先考虑一个串行场景：应用知道目标后发起请求，设备执行重构，端侧等路径就绪后再开始下一轮通信。把时间轴上互不重叠的工作区间写成：

```text
T_ready = T_request + T_service + T_apply + T_settle + T_endpoint
```

- `T_request`：请求准备、去程通信及必经的控制器处理。

- `T_service`：设备服务接收、校验、排队和内部交接。

- `T_apply`：把目标转为设备操作，并调用底层接口。

- `T_settle`：接口调用后仍需等待的物理稳定。

- `T_endpoint`：其余端侧恢复，以及应用必须等待的完成通知。


这里的终点是满足本轮通信的使用条件，API 回复只是其中一种可能的完成依据。

实际实现若有重叠，就应按依赖图的最长路径计算。例如，SDK 已经等待微镜稳定时，不能再额外加一份完整的物理动作时间；端侧恢复与器件动作并行时，也不能简单累加。这个模型的作用，是找出应用真正需要等待的工作，而不是给每个软件层都记一笔包含下游调用的总时长。

暂时忽略端侧恢复，将串行控制成本记为 C、物理重构记为 P，就回到开头的 `T_ready = C + P`。同样的器件提速，遇到不同的控制路径，会得到不同的完整重构时间：

| 串行控制成本 C | P = 20 ms：总等待 | 控制占总等待 | P = 200 μs：总等待 | 控制占总等待 |
| --- | ---: | ---: | ---: | ---: |
| 5 ms | 25 ms | 20.0% | 5.2 ms | 96.2% |
| 500 μs | 20.5 ms | 2.4% | 700 μs | 71.4% |
| 100 μs | 20.1 ms | 0.5% | 300 μs | 33.3% |

表中控制占比按 `C / (C + P)` 计算。

**真正改变架构要求的，是应用留给控制路径多少时间。** 如果把控制预算设为物理重构时间的 10%，即要求 `C / P ≤ 10%`，20 ms 场景允许 2 ms，而 200 μs 场景只允许 20 μs。这个目标让“控制要足够快”变成了可以检查的约束。
### 控制路径上的等待，如何累积到毫秒？
请求与回复在网络中的传输，可以先按字节量估算。假设两者各有 1 KiB 有效载荷，每方向另留 128 B 封装预算，经过两台存储转发交换机、三段链路：无重传时，双向串行化在 1 Gb/s 下约需 55 μs，在 10 Gb/s 下约需 5.5 μs，传播与转发另计。

但字节到达以后，请求还要经过端点处理、设备内部交接和底层接口调用。先固定一条示例路径：**连接已预热、低负载，客户端直接访问设备服务，设备保留独立 Worker，每次重构串行调用两次底层接口，最后同步回复。** 参考现有 Tofino 软件栈的开销量级，可以列出下面这份互不重叠的假设预算；它不是某款 OCS 的通用参数，也不是实测统计区间。

| 一次同步请求的组成 | 示例预算 | 包含的工作 |
| --- | ---: | --- |
| 请求与回复的网络传输 | 10–80 μs | 串行化、传播与交换转发，不含端点软件 |
| 客户端与设备北向处理 | 0.5–1 ms | 收发、编解码和请求分发，不含网络传输 |
| 设备内部交接与非编程工作 | 0.5–2 ms | Worker 交接、校验、排队和状态处理，不含底层调用 |
| 两次底层接口调用合计 | 3–4 ms | SDK client、底层 RPC、运行时处理与调用内等待 |
| **合计** | **约 4–7 ms** | **无独立控制器、有 Worker、两次串行底层调用** |

把各区间端点相加，合计 4.01–7.08 ms，表中取整。预算只计到同步 API 回复，并不代表光路已经可用。主要时间花在端点软件、设备交接与底层调用上，后文将用逐项实测检查这些假设。

对只允许数十 μs 额外成本的应用而言，数百 μs 的交接和调用已经足以超出预算。接下来需要检查的，便是哪些协调必须逐次进行、协议处理需要多少工作，以及设备内部能否减少交接、并行执行。这也对应下面三个架构选择。
## 架构选择：三个可以分别取舍的维度
前面的时间账把问题落到了三个位置：请求是否必须先经过全局控制器、以什么接口进入设备、设备内部怎样把目标落实为连接。它们对应三个可以分别取舍的设计维度：**① 控制器参与方式、② 控制接口与协议、③ 设备执行架构。** 每一项都用同一把尺子衡量：为这部分能力付出的成本，是否在当前预算之内？

| 设计维度 | 可选择的实现 | 主要取舍 |
| --- | --- | --- |
| ① 控制器参与方式 | 逐次协调／提前授权后直接提交，实现逐次转发旁路 | 在线全局仲裁与重复协调成本 |
| ② 控制接口与协议 | 通用 RPC／轻量请求—响应协议 | 工具与协议能力、处理成本及维护责任 |
| ③ 设备执行架构 | 独立 Worker／同进程适配；逐项驱动／批量提交与多通道控制 | 隔离、交接、装载带宽、并发度与收敛依赖 |

![三个设计维度在逐次控制器协调示例中的位置](/ReconfigNet-Sim/images/ocs-control-arch/sdn-control-architecture.svg)

*图 3：沿用电交换网络常见集中式 SDN 协调方式的一个 OCS 集成示例，①②③与上表对应。应用经控制器请求设备，设备服务再通过 Worker 调用 SDK，结果沿调用路径返回。*

三个维度不必一起换边：可以保留通用 RPC，同时允许授权范围内直接提交；也可以换用轻量协议，但继续保留独立 Worker。下面分别估算这些选择可能影响的量级。算例都显式给定条件，目的是找出值得测量的环节；它们不是实测收益，彼此也不能相加，具体组合留到本节最后讨论。
### ① 控制器参与方式：逐次协调，还是提前授权？
如果每次重构都要争用全局端口，控制器在线仲裁就有直接价值：目标连接是否可用，本来就要等全局决策。另一类场景则不同。假设一个通信组在租约有效期内独占一组端口，局部连接变化不会影响其他作业，控制器可以先确定资源边界，组内代表再直接向设备提交。设备仍检查权限、目标和版本，阻止过期执行者继续写入；控制器仍负责监督、回收与故障恢复。**全局状态需要统一管理，并不意味着每次已经获准的局部操作都必须再经过同一个远程执行者。**

后一种分工省掉了重复经过控制器的通信、排队与处理，设备侧必要的校验仍然保留。它也要求系统能够应对代表失效、租约撤销，以及请求结果不明时的接管与状态核对。若资源边界无法提前划清，在线仲裁就不能省略；若能够划清，这一跳便可以从执行路径上移走。

先估算一个量级：若逐次协调比直接提交多出 100 μs 的交互开销、200 μs 的处理与排队，且这些工作无法重叠，提前授权就有机会从执行路径上移走约 **300 μs**。对只允许数十 μs 控制成本的场景，这一跳本身就值得重新安排；具体能否省下，还要看直接提交新增多少设备工作。

除了“谁能提交”，①的取舍还可以沿时间轴展开：执行时还要做多少工作，能否提前完成。可预测的通信阶段若能预先生成目标，设备又支持保存候选状态，运行时可能只需选择并激活候选状态，或按约定时刻触发。授权与配置准备解决的是不同问题：前者确定谁能改哪些资源，后者减少执行时需要生成和装载的工作。存储容量、时钟偏差、计划变更与取消机制，都会影响后者是否可行。
### ② 控制接口与协议：通用 RPC，还是轻量请求—响应？
设备管理需要丰富对象、遥测和成熟工具，通用 RPC 能够复用这些能力；一次时间紧迫的重构，可能只需表达目标连接、授权信息、版本和完成结果。如果通用接口的处理成本满足预算，保留它有利于维护和集成。如果这部分成本已经不可忽略，也可以为执行另设更窄的接口，让 YANG 继续描述连接与状态，gNMI／gRPC 继续承担管理职责。

我们探索过一种轻量分帧实现，下文沿用项目名 framed：以长度前缀划分消息，继续传递 protobuf 请求与响应；北向使用持久 TCP，设备内部交互使用 UDS。它精简了一部分通用 RPC 处理，但错误、超时、重连、背压和完成语义都要自行处理。原有 gRPC 基线同样复用连接，因而不能把差距归因于逐次重建连接；复用数据模型也不意味着 framed 兼容 gNMI。

假设连接、负载和线上传输保持不变，每段完整请求—响应的两端协议处理合计从 200 μs 降到 100 μs，那么一段可省约 **100 μs**，两段串行交互约省 **200 μs**。这里估算的是端点处理，同一份线程交接成本也不能再计入下一项；换成更窄的封装是否有此收益，要测量完整路径后再判断。
### ③ 设备执行架构：从软件交接到并行控制
**③a 软件组织决定请求要经过多少次交接。** 接口接收、语义校验和 SDK 适配是不同职责，但是否需要各占一个进程，要由隔离收益与时间预算共同决定。独立 Worker 可以隔离语言运行时和 SDK 故障，也会增加编解码、socket、线程唤醒和排队。同进程适配可以减少交接，但要求语言与 SDK 支持，也会扩大故障影响范围。职责边界值得保留，进程边界需要说明它换来了什么。

若一次内部往返本身需要 30 μs，额外消息包装和线程投递再需 200 μs，而内联调用新增工作可以忽略，合并这次交接便可能减少约 **230 μs**。这是一组条件估算，不是 UDS 的固定成本。两种组织都需要维护单一写入权威；合并适配进程既不会取消队列，也不会让 SDK 后面的厂商运行时消失，BFRT 到 `bf_switchd` 就是一个例子。

③a 处理的是请求进入设备前后的软件交接，量级在数百 μs；目标进入设备之后，等待就换到另一个尺度：连接目标要经过怎样的器件操作才能落实。

**③b 器件控制决定一个目标要分几步落实。** 一条逻辑连接可能涉及多个 MZI 的相位设置，或两侧多个 MEMS 微镜的姿态调整。把多个操作合进一条命令，可以减少提交成本；设备是否同时装载、同时驱动这些执行器，以及需要几轮反馈才能达到稳定，则是更下一层的能力。**调用次数少，不等于器件已经并行执行；并行启动，也不等于同时完成。**

Apollo 给出了阵列级控制的例子：CPU 经 FPGA、高压驱动和 DAC 设置 MEMS，反馈相机为每个微镜阵列拍摄图像，伺服系统据此调整多个微镜。它并非必须从主机逐镜发起一次完整请求，但阵列级观测与控制，也不足以证明所有光路具有原子切换语义。

硅光同样可以由多通道电子控制器并行驱动。[一项集成电子控制器研究](https://arxiv.org/abs/2501.09664v1)用两颗八通道 ASIC 控制 MZI 网格，并同时启动 16 路反馈。其热调谐执行器的响应约为 10 μs，第一级配置却需约 1.5 ms，四级网格整体约需 10 ms：后级无法在前级设定完成之前完全调好。这是自适应光束耦合实验，并非商用 OCS 切换基准，但它清楚地展示了**执行器响应、反馈收敛和整网格完成**三个不同的时间尺度。

![MZI 与 3D MEMS 的多通道驱动、反馈及执行依赖](/ReconfigNet-Sim/images/ocs-control-arch/device-parallel-control.svg)

*图 4：两类器件的控制结构示意，均为本文自绘，省略封装与部分光学元件。多路电驱动箭头表示并发能力，反馈线表示观测与调整；不表示整台 OCS 的原子切换。底部仅示意等待如何随并发分组与依赖轮次改变，不对应某款产品的时延。*

因此，设备内的执行时间可以继续拆成：命令提交、配置装载、沿依赖轮次收敛，以及最终确认。在每个可独立并行的轮次中，等待由相关通道中最晚完成者决定；轮次之间存在依赖时，还要继续等待。若装载与执行有重叠，就沿实际依赖的最长路径计算，而不是重复计算完整的装载时间。

以一个有意简化的算例来看：假设需要调整 16 个互不耦合的通道，每个通道稳定需 70 μs；配置装载固定为 40 μs，最后确认需 20 μs，提交成本另计，且这些阶段互不重叠：

| 执行方式 | 等待轮次 | 本例设备内等待 |
| --- | ---: | ---: |
| 逐通道驱动，每次等稳定再继续 | 16  | 40 + 16 × 70 + 20 = **1.18 ms** |
| 每组四路并行，组间等稳定 | 4   | 40 + 4 × 70 + 20 = **340 μs** |
| 十六路全部并行 | 1   | 40 + 70 + 20 = **130 μs** |

70 μs 只是本例参数，不是单个 MZI 的统一下限。这笔账说明，除了器件本身快不快，还要问：有多少执行器需要改变状态、驱动器能并发多少路、配置字节能多快装载，以及反馈需要跨越几级依赖。若需装载 B 字节、有效速率为 R 字节／秒，仅装载就至少需要 B/R 秒；这笔传输成本仍然省不掉。通道更多、带宽不足或热耦合需要反复修正，都可能重新拉长关键路径。商用设备给出的亚毫秒指标，也不足以反推其内部具体的控制机制。
### 把三个选择组合成一种候选分工
有了这三个维度，才可以讨论具体组合。考虑这样一类快速重构场景：资源能够提前分配，设备可以校验授权，SDK 又允许同进程适配。一种值得检验的候选分工是：控制器提前完成资源协调，之后只负责授权、监督与回收；组内代表通过轻量请求—响应协议直接提交；设备在同一进程中完成校验与 SDK 适配，经单写入队列把批量目标交给厂商控制栈；最后由设备按自身驱动并发度和反馈机制落实目标，按约定报告结果。与图 3 相比，这个组合在三个维度上都取了精简端，但它只是众多组合之一——也可以只换其中一项，其余维持原状。

![提前授权、直接提交与同进程适配的候选组合](/ReconfigNet-Sim/images/ocs-control-arch/candidate-architecture.svg)

*图 5：三个维度的一种候选组合，与图 3 使用相同角色位置。虚线表示提前授权、监督与回收，实线表示逐次请求、设备调用和结果返回。设备保留校验、单写入队列及厂商运行时；下层并发与收敛能力仍需单独核实。该组合尚未完成端到端验证。*

沿着两幅架构图，可以检查哪些工作提前完成了，哪些交接合并了，哪些设备成本仍然存在。下面先说明实验平台，再看现有证据能支持哪些判断。
## 实验平台：用 Tofino 检查控制路径
要把这些架构选择落实为可检查的时间账，首先需要一个能反复修改、又能观察实际连通变化的平台。真实 OCS 的器件路线、规模、软件配套和可得性差异很大，实验室很难为每次控制架构调整都搭建完整光学环境。ReconfigNet-Sim 的目标，是让交换机之外的控制与集成工作能够提前开始，并提供可控制的连接变化来检验它们。

沿用前面的框架，Tofino 也接收连接意图，由 Agent 校验和转换，再经厂商控制接口执行。区别集中在后半段：BFRT client 通过本机 gRPC 调用运行时服务 `bf_switchd`，写入 P4 许可表，改变逻辑端口间是否允许转发。这个过程中，电链路持续在线；它提供实际的软件、运行时和硬件控制路径，但不复现光路切换及恢复。

![真实 OCS 与 Tofino 在统一框架下的功能对应](/ReconfigNet-Sim/images/ocs-control-arch/platform-comparison.svg)

*图 6：本文绘制的功能对照。两侧对应连接请求、设备控制和连通变化三个层级，底层物理机制不同。Tofino 的表项变化不能代替光功率稳定、波长调谐、BER、PHY 训练或 NIC 恢复；P4 还会解析和处理分组，也不具有真实 OCS 的协议透明性。*

这使它适合回答“软件交接需要多久”“厂商运行时调用占多少预算”等问题，并用真实转发检查一部分控制优化的效果。本文使用物理 Tofino-1 的既有测量，没有把软件模型 CI 视为实机验证，也没有将测得的软件延迟直接外推成某款光交换机的完整重构时间。[项目边界说明](https://github.com/ZER0-Nu1L/ReconfigNet-Sim/blob/main/docs/ocs-simulation-principles-and-boundaries-zh.md)给出了更完整的区分。
## 实验证据：路径、进程与设备调用
实验采用物理 Tofino-1、BF-SDE/BFRT 9.3.1 和 Pentium D1517 控制 CPU，连接预热后由单写入流反复提交有变化的目标。共同设置为 DELTA 更新、批量设备调用、零人为 gap，以及 `CACHED_ACK`：等待南向调用成功后提交缓存，不逐次同步回读。

在共同设置之上，后面对照了四组变体：

- **整体路径对照**：约 800 MHz，客户端跨管理网访问，比较完整 gRPC 路径与组合优化，两组各 5 轮、每轮 2,000 次切换；
- **进程组织对照**：约 800 MHz，设备主机本机 TCP，比较 Go Core＋Python Worker、Python 单进程与 Go 单进程，每轮 200 次热写；
- **调用次数对照**：约 1.2 GHz，同样为本机 TCP，比较两次 BFRT 请求与合并为一次，每轮 200 次热写；
- 这些变体保存在独立开发分支，尚未全部成为公开仓库的正式部署选项。

现有测量主要覆盖②控制接口与协议、③设备执行架构中的软件交接与厂商调用，没有测量独立控制器这一跳，也没有验证光器件的并行收敛。我们依次看整条路径的组合改善、设备进程组织，以及上层精简后的设备调用成本。进入结果前，先区分需要观察的事实：

| 指标  | 计时范围 | 用途  |
| --- | --- | --- |
| API 延迟 | 客户端发起操作 → 收到回复 | 调用者等待接口多久 |
| 设备编程区间 | 后端开始编程 → 设备接口调用返回 | SDK、底层 RPC、运行时处理与等待的合计 |
| 新路径观测延迟 | 提交请求 → 首个新路径探针回包 | 何时观察到新路径能够传包 |
| blackout | 最后旧路径回包 → 首个新路径回包 | 探针观察到的切换空窗 |

这些指标从不同位置观察同一次操作，不能相加。API 回复与新路径回包没有固定先后，探针还包含发送间隔和收包调度。软件分段则沿嵌套调用逐请求相减，再统计残差：例如 `非设备区间 = API 总历时 − 设备编程区间`。不能将 Worker 总时长再加上它已经包含的 BFRT 调用，也不能直接相减不同区间的 p99；下文分位数统一使用 nearest-rank。
### 整体路径：组合优化带来了多少改善？
**减少控制路径上的软件工作，确实让新路径更早被观察到；但转发生效与断流窗口的改善并不等比例。** 第一组实验保留设备侧删除后安装的两个 BFRT 调用，对照原有完整 gRPC 路径和一套组合优化。

基线为“远端客户端 → gRPC 北向 → Go Core → 本地 gRPC Worker → Python 专用执行线程 → BFRT”。组合候选换用 framed 北向和 Worker 交互，精简成功回复，减少线程投递，并调整 CPU 亲和性。这组组合仍保留 Python Worker，尚未采用图 5 的同进程适配。两组各做 5 轮、每轮 2,000 次成功切换，使用目标间隔 20 μs 的忙轮询探针。

| 方案  | 新路径观测 p50 | 新路径观测 p99 | blackout p99 |
| --- | ---: | ---: | ---: |
| 完整 gRPC 分进程基线 | 4.914 ms | 5.490 ms | 2.776 ms |
| framed、减少交接、精简回复及绑核的组合 | 3.320 ms | 3.817 ms | 2.490 ms |

新路径观测 p99 降低约 30.5%，blackout p99 降低约 10.3%。请求更早得到处理，会缩短触发后的总等待；数据面切换空窗还受设备执行等因素影响。收益属于整套配置，其中包括 CPU 亲和性的变化，不能单独归功于 framed。两组实际探针间隔 p99 约为 24／22 μs，结果也不能再机械扣去一个“20 μs 测量误差”。

这里的 baseline 已经包含完整 gRPC 和设备内部交接，但客户端直接请求设备，没有经过独立的全局控制器。**这组数据支持精简设备执行路径，并未测出绕过集中式控制器的收益。** 前面候选方案中的授权下放仍是一项需要端到端补测的架构判断。
### 预算分解：毫秒级等待花在了哪里？
前面的假设路径保留独立 Worker 和两次底层调用。现有 API 测量恰好覆盖这一结构，可以用来检查预算的量级。完整 gRPC 基线与组合优化各汇总 5 轮、每轮 2,000 次，把每次请求的嵌套计时先相减、再取均值，得到互斥预算：

| API 预算项，均值 | 完整 gRPC 基线 | 组合优化＋绑核 |
| --- | ---: | ---: |
| 客户端／北向剩余区间 | 847.4 μs | 532.5 μs |
| Core 自身，不含 Worker 调用 | 58.2 μs | 59.3 μs |
| Worker RPC 剩余，不含 Worker 内部 | 1,167.7 μs | 364.2 μs |
| Worker 内部，不含设备编程 | 701.4 μs | 294.3 μs |
| BFRT 设备编程区间 | 3,818.1 μs | 3,144.5 μs |
| **API 总计** | **6,592.8 μs** | **4,394.8 μs** |

这里每次删除六条、插入六条表项，仍分成两次 BFRT 调用；上面的数据面探针对照每次各删、插四条。它们是不同的请求与测量，不能将 API 均值与新路径 p50/p99 对齐解释。客户端／北向剩余区间约为 0.85→0.53 ms，包含外部网络往返；Core、Worker 交互及内部非编程工作合计约为 1.93→0.72 ms，两次 BFRT 调用合计约为 3.82→3.14 ms。API 总均值约为 6.59→4.39 ms，与前面约 4–7 ms 的假设量级相符。**假设预算帮助定位等待，逐项测量才能确认当前实现的成本。**
### 进程组织：单进程与多进程相差多少预算？
第二组对照回到③a的软件组织。在相同本机客户端、约 800 MHz 和 framed 接口下，既有记录包括 Go Core 加 Python Worker、Python 单进程 Agent，以及 Go 直接调用 BFRT 的单进程方案。每轮各有 200 次热写，仍使用两个 BFRT 调用；Go 单进程的两轮分别列出：

| 实现  | 非设备区间均值 | 非设备区间 p99 |
| --- | ---: | ---: |
| Go Core＋Python Worker | 1,003.3 μs | 1,272 μs |
| Python 单进程 | 667.1 μs | 924 μs |
| Go 单进程，轮次 A | 307.0 μs | 408 μs |
| Go 单进程，轮次 B | 302.8 μs | 570 μs |

与分进程实现相比，Python 单进程的非设备均值减少约 336 μs；Go 单进程两轮则落在约 303–307 μs。这个数在数 ms 预算中可能只是一部分，但在数十至数百 μs 预算中，可能直接决定方案是否可行。即使都在同一台设备主机，进程、运行时与调度边界也值得逐项检查。

![整体路径与设备进程结构的独立对照，含 Go 单进程两轮](/ReconfigNet-Sim/images/ocs-control-arch/latency-comparison.svg)

*图 7：左图为整体路径对照，右图为进程组织对照；指标、轮次与实现不同，不组成连续加速曲线，线段也不是置信区间。*

这些实现同时涉及语言、协议库与调度方式的变化，即使都使用 Go，也未固定所有软件条件，因而不能把差值全部归给进程边界。当前数据支持把交接纳入预算；要单独归因，仍需固定语言、北向接口和后端，只改变进程组织。语言对照选 Python 与 Go，是因为前者是解释型、后者是编译型（与 C/Rust 同类），用来观察“去掉解释器”这一维度的量级；它不是语言性能排名。

重复目标还可以复用已完成的配置转换。既有 Python 单进程记录中，关闭记忆化的三轮与开启后的四轮，各轮均为 200 次热写，非设备均值的轮均值从约 694.1 μs 降至 635.7 μs，相差约 **58.3 μs**。这是重复目标下少做软件工作的证据，不是预装载器件配置或快速激活的实测收益；新目标仍可能需要重新生成和装载。这里的差异只有几十 μs，插桩方式必须一致：当前嵌入式 Python 环境一次 `monotonic_ns` 约需 2.193 μs，每请求读取 8–10 次，仅取时就约占 18–22 μs，足以掩盖记忆化的效果。
### 设备调用：上层精简以后，还剩多少成本？
进程结构只是控制路径的一部分。后续调用次数对照继续使用 Go 单进程直接调用 BFRT，在约 1.2 GHz 下保留持久 framed、精简回复和 CPU 亲和性。**即使上层已经明显缩短，设备编程仍占据这条路径的大部分时间。** 对硬件厂商而言，能够多快地把一个目标落实为设备状态，本身就是快速重构能力的一部分。

我们用一个局部对照展示这件事：将删除、安装分成两个 BFRT 请求，与合并为一个请求比较。每轮预热 50 次后记录 200 次 changed write；客户端在设备主机上运行，不包含外部管理网往返。

| Go 直连方案 | API p50／p99 | 设备编程 p50／p99 | 非设备区间 p99 |
| --- | ---: | ---: | ---: |
| 两次设备请求 | 852／1,174 μs | 715／998 μs | 202 μs |
| 一次请求，轮次 A | 625／782 μs | 490／591 μs | 203 μs |
| 一次请求，轮次 B | 622／1,021 μs | 486／751 μs | 215 μs |

少一次调用，设备编程 p50 减少约 0.23 ms，非设备部分基本不变。合并请求是一个具体的实现手段，它揭示的接口问题更普遍：**一次重构需要多少个串行调用，每个调用又带着多少固定处理与等待，都会进入执行预算。** 这些步骤是否可以合并，是否需要由调用者逐项驱动，值得在设备接口设计时一起考虑。

![同一 Go 直连条件下的 API 与 BFRT 编程区间](/ReconfigNet-Sim/images/ocs-control-arch/runtime-cost.svg)

*图 8：分别显示两次请求与单次请求下 API、设备编程区间的 p50／p99，二者为包含关系，不能相加。*

约 0.5 ms 的编程区间包含 BFRT client、本机 gRPC、`bf_switchd`、调度和调用等待，尚未拆出纯硬件时间。作为分界参考，同一原子写在 Python BFRT 客户端下约 2.4 ms、Go 客户端下约 0.49 ms——换语言能压缩客户端部分，服务端往返仍在；两组轮次与结构不同，只用于说明客户端与服务端的分界，并非同条件对照，也不构成 ASIC 或 OCS 的物理下限。

合并请求使用的 `ROLLBACK_ON_ERROR` 只描述错误处理策略，实验也没有提供数据面原子切换保证。这一对照对应的是③b中的提交粒度，MZI 或微镜的并行驱动仍未测量。

光子系统也有驱动单元主导整机时间的实证。[2024 年一篇 Nature Communications 论文](https://www.nature.com/articles/s41467-024-45888-7)介绍的通用可编程光子处理器，由可编程电流源阵列控制 304 个相位执行器；作者明确报告，设置与读回由驱动单元主导，系统重构需 **15–90 ms**。它是面向射频应用的处理器，与 ONE-32 不是同一产品，不能用来替代当前商用 OCS 的指标；但它说明，执行器之外的驱动与读回架构，足以成为系统重构的主导项。

BFRT 让我们看到配置提交的成本；λλ 则进一步提醒我们，配置生成也可能包含需要认真对待的工作。它提供更强的光子编程能力，编译器需要把程序映射到具体硬件。对于快速重构，重要的是区分**生成新配置需要多久、装载需要多久，以及选择并激活已有配置需要多久**。只有必须逐次在线重新生成的部分，才会进入每轮执行路径；能够提前完成的编译与映射，应计入准备阶段。

因此，不能仅凭复杂编译就认定可编程光交换失去了快速切换能力。更值得向设备与软件栈提出的问题是：高层目标变化时，哪些成本必须在线支付？已知目标能否提前准备，运行时又能用什么接口快速激活？本文引用 λλ 来说明配置生成这一职责；其具体编译时延及实验条件尚待全文核实，不据此推断逐次切换性能。

负载也会改变这笔账。仅作一个排队估算：若单写入服务固定需要 0.5 ms，请求以每秒 1,600 次的泊松过程到达、由单服务者先到先服务，利用率便达到 80%。按 M/D/1 模型，平均排队约为 1 ms，加上服务共约 1.5 ms；这不是实测尾延迟，而是提醒我们，空闲时满足预算的路径，在持续负载下仍可能失约。

现有结果支持的是：软件组织与设备接口都会影响完整执行路径，而不同位置的优化带来不同收益。接下来最值得补齐的两项证据，是固定设备路径后测集中式转发与直接提交，以及固定语言和接口后测单／多进程。它们将分别检验逐次全局参与和设备内部隔离的成本，避免把组合结果误解成某一个架构选择的全部效果。

需要说明的是，本文实验结果是既有现场探索的脱敏汇总，原始日志、部署配置和源码快照保留在私有实验记录中，目前只提供架构探索证据，尚不是已公开、可独立复现的性能基准；公开代码中的正式接口也不包含本文所有实验变体。关于原始依据、公开出处和后续需要补充的材料，另在写作区的 `sources.md` 中记录。
## 软件路径的时间下限：通用 CPU 形态还能多快？
把上面的维度压到极限，仍会碰到一组不随优化消失的成本。它们不是某个协议的实现细节，而是“通用 CPU + 操作系统 + 管理协议”这种形态的固定开销：

| 结构层 | 量级  | 说明  |
| --- | ---: | --- |
| 系统调用 / 线程唤醒与切换 | 0.1–2.5 μs/次 | 每次交接都要付 |
| 内核网络栈（单包单方向） | 数–20 μs | 旁路后可降到 1–3 μs，但已不是原形态 |
| PCIe 设备读写 | 0.3–1 μs | 与 CPU 频率基本无关 |
| 管理协议端到端 | 10¹ ms | SONiC 官方遥测单轮 68 ms（大计数器集）；gNMI 配置仅比 NETCONF 快 1.5–3× |

频率对照说明同一件事：800→1200 MHz，只有 CPU-bound 段按比例缩短（实测比值 0.55–0.70），固定成本几乎不动。因此“换更快的 CPU”不能改变量级。

把这些固定成本全部拆掉（同机共享内存、内核旁路、零分配、实时调度），软件路径的极限大约在 **20 μs（p99）**，绝对下限约 **4–8 μs**（估算）；再往下就必须离开通用 CPU/OS 形态。作为对照，FPGA 控制面的建链决策可到 **500 ns**，完整建链实测 **8.36 μs**；JOCN 的目标线是 **20 μs（含硬件设置）**。

所以，上限来自 **SDN 形态的成本结构，而不是 CPU 本身**。对 MEMS（30–200 ms），这条上限无关紧要——控制预算 1.5 ms 只占物理时间的 5%；对硅光（约 200 μs），它直接决定标准化能否支撑动态重构。若要把端到端压到 200 μs，还需要驱动级编程（本平台经 `bf_switchd` 的一次写入就要 0.35–0.72 ms），仅靠上层协议与进程优化不够。
## 场景取舍：怎样组合这三个选择？
三个设计维度并没有共同的最优选项。同一个接口，对低频拓扑调整和逐阶段重构可能有完全不同的意义：前者更容易摊薄配置成本，后者可能在每轮通信前都等它完成。要判断怎样组合，可以先看两个场景条件：应用留给控制路径多少时间，以及目标能否提前知道。

| 控制预算 | 目标随请求才确定 | 目标可以提前准备 |
| --- | --- | --- |
| 较宽，例如允许数 ms 额外成本 | 优先评估通用管理接口与进程隔离，同时检查排队 | 可沿用通用接口，再判断提前准备是否值得 |
| 较紧，例如只允许数十至数百 μs | 减少必经协调和交接，检查在线转换、SDK 与尾延迟 | 研究预生成、预装载、定时或本地触发，核实设备能力 |

右列描述的是另一种应用前提，当前实验没有验证预装载与快速激活的端到端收益。即使可以提前准备，容量占用、计划变更、时钟误差、取消和恢复也需要预算。相反，一个器件很快、使用却很低频的场景，也可能合理地优先选择隔离与可维护性。

回到三个维度：资源能否提前划分、工具与互操作需求的分量、隔离收益与底层并发能力，分别约束着三项选择。控制预算紧，并不自动意味着三个维度都选更精简的一端，也可能意味着需要进一步研究设备侧预装载和本地触发。

对具体系统，顺序应当是：先明确应用何时需要路径、什么事实算就绪，再找出必须在线完成的协调与执行，最后组合可满足预算的实现。厂商接口需要多少步、配置要装载多少字节、执行器能够并发多少路，以及反馈要等几轮，也要在这个过程中一起检查。
## 结语：让控制架构跟上器件的速度
回到开头的落差：当物理重构从 20 ms 缩短到 200 μs，5 ms 串行控制就会把完整重构留在毫秒级。要让器件迭代体现为更快的连接使用，需要先划清规划与执行，再分别检查①控制器参与方式、②控制接口与协议、③设备执行架构，并核对底层驱动与反馈能否跟上预算。

OCP 的快速 OCS 材料已经呼吁统一端到端指标，Zero-Touch 演讲也明确提出“A common API stack is not enough”，要求共同服务语义和路径验证。本文进一步把这个问题落到执行架构：哪些工作应该提前完成，哪些位置必须逐次参与，在线剩下的工作又能否满足应用预算？

Tofino 的观察给出了部分回答：减少软件工作可以让新路径更早被观察到，不同设备进程实现的非设备区间相差数百 μs，精简上层以后厂商运行时调用仍可能主导剩余时间。真实光器件上的完整验证和集中式路径补测还需要继续，但这条设计要求已经很明确：**器件每快一个数量级，控制架构就需要重新接受一次预算检验。否则，微秒级的器件，仍可能交付毫秒级的重构。**
